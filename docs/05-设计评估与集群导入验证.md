## 1. 评估基准：官方文档确立的设计理念

先立基准，再看本工具偏离在哪。以下均为官方文档原文。

| 官方约束 | 原文要点 | 来源 |
| --- | --- | --- |
| 集群必须逐节点备份 | "To make a complete backup for VictoriaMetrics cluster, `vmbackup` must be run on each `vmstorage` node in cluster." | [vmbackup](https://docs.victoriametrics.com/victoriametrics/vmbackup/) |
| 各节点备份必须分开存放 | "Backups must be placed into different directories on the remote storage in order to avoid conflicts between backups from different nodes." | 同上 |
| 快照无需跨节点同步 | "Snapshots may be created independently on each `vmstorage` node. There is no need in synchronizing snapshots' creation across `vmstorage` nodes." | [cluster](https://docs.victoriametrics.com/victoriametrics/cluster-victoriametrics/) |
| 还原是 rsync --delete 语义 | "the contents of -storageDataPath dir is synchronized with -src contents, i.e. it works like 'rsync --delete'" | [vmrestore](https://docs.victoriametrics.com/victoriametrics/vmrestore/) |
| 数据按一致性哈希分片 | "`vminsert` … spreads it among `vmstorage` nodes according to consistent hashing over metric name and all its labels" | [cluster](https://docs.victoriametrics.com/victoriametrics/cluster-victoriametrics/) |
| 历史数据不必在哈希对应节点上 | "This enables writing new data only to new `vmstorage` nodes, while historical data from old `vmstorage` nodes remain available for querying via `vmselect` together with the newly ingested data." | 同上 |
| 单节点与集群备份不可互通 | "Backups created from single-node VictoriaMetrics cannot be restored at cluster VictoriaMetrics and vice versa." | [vmbackup](https://docs.victoriametrics.com/victoriametrics/vmbackup/) |

## 2. 设计合理性评估

### 2.1 与官方理念一致的部分（判定：合理）

| 设计决策 | 官方依据 | 判定 |
| --- | --- | --- |
| 零侵入，只 import 不 fork `lib/backup/**` | 官方备份格式是"按 part 路径寻址的远端对象集合"，`vmrestore` 不做清单校验 | ✅ 地基正确 |
| 过滤点放在"源端列举之后、上传之前" | `Backup.Src` 是具体类型 `*fslocal.FS`（非接口），`runBackup()` 包内私有 → 无注入点 | ✅ 唯一可行点 |
| 月分区判据用 7 字符 `YYYY_MM` | `lib/storage/time.go` 的 `timestampToPartitionName()` = `t.Format("2006_01")`；part 目录名是 16 位十六进制，不可能混淆 | ✅ 判据安全 |
| 审计文件用 `.ignore` 后缀 | `lib/backup/fscommon/fscommon.go` 的 `IgnorePath` 只判后缀，所有远端 `ListParts` 都调用它 | ✅ 零污染 |
| `backup_complete.ignore` 先删后建 | 官方 `runBackup()` 同一时序：完成标记存在才代表备份可用 | ✅ 语义一致 |
| 集群各节点写独立目标目录 | 官方明确要求不同节点放不同目录 | ✅ 与官方一致 |
| 快照可独立创建、无需跨节点同步 | 官方明确允许 | ✅ 编排脚本设计正确 |

### 2.2 与官方理念的偏离（判定：可控，但必须明确告知）

**偏离点：官方 vmbackup 的设计前提是"完整备份整个存储"，本工具做的是"部分备份"。**

官方文档没有任何"部分备份"的表述，反而通过"必须在每个 vmstorage 上运行"来**隐含要求完整备份**。本工具把"完整"这一前提改成了"按月份子集"。

这个偏离之所以成立，靠的是两条源码事实（已在 `docs/01` 论证）：

1. 备份产物不依赖 `parts.json`，远端对象由 `common.Part.RemotePath()` 寻址、`ParseFromRemotePath()` 反解
2. 月分区目录是自包含的：`data/{small,big,indexdb}/<YYYY_MM>/` 下同时含该月的数据 part 与 indexdb part

→ 抽走若干月份后，剩余部分仍是一个**自洽的、合法的** VictoriaMetrics 备份。

**风险定性**：属于官方未支持的扩展用法。产物格式合法、可还原、可启动、可查询（已实测），
但它**不是**原集群的完整副本——这一点必须在运维上被明确认知，不能当作灾备全量备份使用。

### 2.3 一条官方说法在 v1.150.0 需要重新理解

官方说"单节点与集群备份不可互通"。但源码与实测显示：

- `lib/storage/storage.go`：`tablePath := filepath.Join(path, dataDirname)`，集群 vmstorage 与单节点**共用同一套存储布局**，无额外租户层级
- v1.150.0 中 `app/vmstorage` 是 `package vmstorage`（库），被 `app/victoria-metrics/main.go` import；`victoria-metrics` 二进制通过 `-vmselectAddr` 即可"as if it were vmstorage"
- **实测**：把集群中 node0 的备份还原到单节点 `victoria-metrics`，可正常启动并查出 `2026_02`~`2026_06`

→ 在 v1.150.0 这一条**在格式层面不成立**。官方该表述更可能指旧版本，或指"数据完整性语义"
（集群备份只还原一个节点 = 只有部分数据）。评估结论以实测为准，但仍建议按官方口径谨慎使用。

## 4. 完整度评估：缺陷清单

### P0 · `-retentionPeriod` 未警示 —— 会导致数据丢失（**已修复**）

**问题**：按月备份装的是**过去**的月份。还原后若用默认 `-retentionPeriod=1M` 启动，
VictoriaMetrics 会在后台 merge 时把超出保留期的 part 全部丢弃
（`lib/storage/partition.go`：`retentionDeadline := timestampFromTime(startTime) - pt.s.retentionMsecs`）。

**实测证据（v1.150.0，还原 `2026_02`~`2026_06` 后以默认保留期启动）：**

```
t=0s    可查=[2026_02 2026_03 2026_04 2026_05 2026_06]   磁盘分区=[2026_02 .. 2026_06 2026_09]
t=50s   可查=[2026_02 2026_03 2026_04 2026_05 2026_06]   磁盘分区=[2026_02 .. 2026_06 2026_09]
t=75s   可查=[]                                           磁盘分区=[2026_09]
```

约 1 分钟后历史分区被清空，磁盘只剩当前月。

**这是最严重的缺口**：原 README 与 `docs/03` 完全没有提及，按原文档操作必然丢数据。
**已补入 `README.md` / `README_CN.md` 的"还原与验证"章节与 `docs/03 §5.0`。**

### P0 · vmrestore 的 `rsync --delete` 语义未警示（**已修复**）

官方文档：目标目录非空时内容被同步替换，等同 `rsync --delete`。
导入到已在运行的集群节点会删掉现有月份。**已补入文档。**

### P1 · 集群导入场景未纳入端到端回归

原 e2e 只覆盖单节点还原。本次评估补充了真实 3 节点实验（见 §5），
但**尚未脚本化**。建议新增 `scripts/e2e-cluster.sh` 纳入回归。

### P2 · 文档未说明"变更节点数"时的行为

官方明确：新增 vmstorage 后"历史数据留在旧节点，仍可被 vmselect 查询"。
这意味着**导入到节点数不同的新集群也可查**，只是数据分布与哈希不一致。
文档目前只强调"必须独立目录"，未说明这一点。

### P3 · 备份元数据未记录源集群拓扑

`backup_month_range.ignore` 记录了月份范围，但**没有记录节点数、节点名、VM 版本**。
跨集群导入时，这些信息对"还原到几个节点、对不对得上"很有价值。建议补充字段。

## 5. 核心问题：按月备份导入新 VictoriaMetrics 集群后是否可用？

### 5.1 实验设计

真实 3 节点环境（v1.150.0 的 `victoria-metrics` 以 vmstorage 模式运行）：

```
① 源集群 c1：3 节点，retention=100y，灌入 2026_01~2026_09 共 9 个月、按序列分片
② 逐节点快照 + 本工具按月备份 [2026_02 .. 2026_06]，写入 3 个独立目标端
③ 停源集群
④ 用官方 vmrestore 还原到新集群（3 个空目录，节点一一对应）
⑤ 启动新集群并查询；再写入当前月新数据，验证新旧共存
⑥ 对照组：同一份备份，用默认 retention 启动
```

### 5.2 实验结果

| 检查项 | 结果 |
| --- | --- |
| 备份产物只含所选月份 | ✅ `bak/node{0,1,2}` 均只有 `2026_02`~`2026_06` |
| 还原到新集群后可查询（retention=100y） | ✅ 三个节点均返回 `2026_02 .. 2026_06` |
| 新写入当前月数据后 | ✅ 新旧共存，历史月份仍在，被排除的 `2026_01` 不可见 |
| 还原到单节点实例 | ✅ 可启动并查询（v1.150.0 存储层统一） |
| **默认 retention=1M 启动** | ❌ **约 75 秒后历史数据被全部删除** |

### 5.3 结论

**可用，但有三个硬前提：**

1. **`-retentionPeriod` 必须覆盖数据跨度**（否则数据被自动删除 —— 这是最容易被忽略、后果最严重的一条）
2. **每个 vmstorage 的备份还原到对应的节点、各自独立的空目录**（与官方"逐节点备份、分目录存放"一致）
3. **不要用 `rsync --delete` 语义覆盖掉目标节点上已有的数据**

**可用性的边界**：

- 导入后得到的是一个**只包含所选月份**的存储实例，不是原集群的完整副本
- 查询侧没有障碍：`vmselect` 会向所有 vmstorage 广播查询并合并，
  官方也明确"历史数据留在旧节点仍可被查询"，因此即使数据分布与一致性哈希不一致也能查到
- 若新集群节点数与原集群不同，数据分布会与哈希不一致；官方虽未禁止，
  但会失去副本与负载均衡的原有语义，建议**保持节点数一致**

## 7. 生产实测补记（v1.0.1，2026-09-24）

本节记录本工具**第一次真实生产运行**暴露的问题与结论。节点名与路径已匿名化。

### 8.1 运行概况

| 指标 | 值 |
| --- | --- |
| 目标 | 集群版 vmstorage 节点（3 节点集群中的第 2 个） |
| 备份区间 | `2025_03` ~ `2026_06` |
| 保留 | 5069 part / 890,859,936,109 字节（≈830 GiB） |
| 排除 | 694 part / 16,375,958,510 字节（`2026_07`~`2026_09`，≈15.3 GiB） |
| 耗时 | ≈24 分钟（`-concurrency=10`，本地 `fs://` 目标端） |
| 账目 | `du -sh` 与 `bytes_kept` 完全一致 |

**数据起点实测为 `2025_03`，与 `months_present_in_snapshot` 一致** —— 这正是
`-expectMonths` / dryRun 防呆设计的价值：月份边界应来自实测，而不是凭印象。

### 8.2 新发现：legacy indexdb 位于顶层（文档此前未覆盖）

备份产物中出现 `indexdb/`（顶层）而 `data/indexdb` 不存在。核对源码后确认这是**合法布局**：

- 现代布局：`<storageDataPath>/data/indexdb/<YYYY_MM>/`（`table.go:110`）
- legacy 布局：`<storageDataPath>/indexdb/`（`storage.go:275` `legacyIDBPath`），
  由 `legacyCreateSnapshot()`（`storage_legacy.go:232`）链接进快照**顶层**
- 两者可并存（老版本升级而来的集群），该集群即属此例

对本工具的影响：`Classify` 要求路径首段为 `data`，因此顶层 `indexdb` 被归为**非分区**，
随 `-includeNonPartitioned=true` 整体保留。**这是正确行为**——legacy indexdb 按
`prev`/`curr` 划分时间范围，无法按自然月切分，整体保留才能保证还原后索引完整。

由此可推出一条对使用者很重要的结论：**本工具不可能漏备**。
过滤只丢弃「位于严格 `YYYY_MM` 目录内、且月份在区间外」的路径，其余一律保留。

### 8.3 快照机制的补强结论（影响"备份是否影响业务"的答复）

逐行核对 `lib/storage` 后确认：

- **part 数据用硬链接**：`partition.go:1865` `fs.MustHardLinkFiles`，
  官方注释 "Snapshot is created using linux hard links, so it is usually created very quickly"
  → 不复制字节、不占额外空间，且**原 part 被 merge/retention 删除后 inode 仍在，备份不会中途读失败**
- 快照入口目录（`data/{small,big,indexdb}`、顶层 `indexdb`）是相对符号链接（`lib/fs/fs.go:205`）
- `snapshot/` 目录与分区目录**同级**，故 retention 删整月分区不会波及快照副本
- 每个 partition 先 `flushInmemoryRowsToFiles()`（`partition.go:1827`），
  是快照阶段唯一会短暂影响写入的点
- **`-maxBytesPerSecond` 对 `fs://` 同样生效且作用在读侧**
  （`fslocal.go:37-39` 建立 `bandwidthLimiter`），是保护源盘 IO 的正确旋钮

### 8.5 还原侧新增的一条工程约束

`vmrestore` 将备份**实体写**到目标目录，**需要一份与备份等量的可用空间**，不吃硬链接、不去重。
磁盘紧张时的替代方案：备份目录本身即标准存储布局，可在**同文件系统**内 `cp -al` 硬链接克隆后
让单机二进制直接加载（`df` 几乎不变），验证完删除克隆即可。详见 `docs/03` §5.0③。
