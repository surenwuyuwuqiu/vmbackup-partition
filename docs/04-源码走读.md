## 2. `internal/monthfilter` —— 月份识别与过滤

### 2.1 `month.go`：事实基础

**`Month` + `Parse`（month.go:31-55）**

`Parse` 接受 `YYYY_MM` / `YYYY-MM` / `YYYYMM`，内部统一归一为 `YYYY_MM` 后交给 `time.Parse("2006_01", …)`——**复用与官方完全相同的布局常量**，因此不可能出现"自定义解析规则与 VM 不一致"的问题。

**`IsMonthDirName`（month.go:82-100）**：这是过滤正确性的基石。

```go
func IsMonthDirName(name string) bool {
	if len(name) != 7 || name[4] != '_' {
		return false
	}
	for i, c := range name {
		if i == 4 {
			continue
		}
		if c < '0' || c > '9' {
			return false
		}
	}
	month := int(name[5]-'0')*10 + int(name[6]-'0')
	if month < 1 || month > 12 {
		return false
	}
	_, err := time.Parse("2006_01", name)
	return err == nil
}
```

**为什么可以放心用"严格 7 字符"作为判据？** 因为 VM 的 part 目录名是 **16 位十六进制**（如 `0000000000000001`、`08150E632450B550`），长度 16 且含大写字母，与 `YYYY_MM` 不存在任何交集。`TestIsMonthDirName` 覆盖了这一点（对 16 位 hex 名字返回 false）。

**`Range`（month.go:103-145）**

- `Index() = Year*12 + (Month-1)`：把"年月"降维成一个单调整数，于是区间判断、排序、跨年展开都退化为整数运算，**从根本上消除跨年比较的边界 bug**。
- `ParseRange` 在 `to < from` 时直接返回错误——这是第一道护栏。

### 2.2 `filter.go`：分类与聚合

**`Classify`（filter.go:63-87）**

```go
segs := strings.Split(path, "/")
if len(segs) < 3 || segs[0] != DirData {
	return c                                    // 非 data/ 开头 → 非分区
}
for i := 1; i <= maxPartitionProbeDepth && i < len(segs); i++ {
	if !IsMonthDirName(segs[i]) {
		continue
	}
	...
	return c                                    // 找到 YYYY_MM → 分区路径
}
return c                                        // 未找到 → 非分区
```

- 首段必须是 `data`：`metadata/…` 天然落入"非分区"分支。
- `maxPartitionProbeDepth = 3`（filter.go:39）：官方布局是 `data/<sub>/<YYYY_MM>/…`，探测深度 1 就够。放宽到 3 是为对"中间多插一层"的布局变体保持稳健。
- **放宽不会引入误判**（这一点在 filter.go:36-38 的注释里论证了）：`data/` 之下只可能是 `small|big|indexdb`，其下只可能是 `YYYY_MM`，再往下只可能是 16 位 hex 的 partID，part 目录之下只有数据文件。因此除了分区目录本身，不可能再出现严格形如 `YYYY_MM` 的目录名。

**`Filter.Decide`（filter.go:104-110）**：决策逻辑全部集中在这 6 行。

```go
c := Classify(path)
if !c.Partitioned {
	return c, f.IncludeNonPartitioned      // 非分区 → 由开关决定
}
return c, f.Range.Contains(c.Month)        // 分区   → 必须落在区间内
```

**`Aggregator`（filter.go:150-231）**

设计目标是**流式**：`Add(path, size)` 逐 part 累加，内存占用与 part 数量无关（除了一个按月份聚合的 map，其条目数 ≤ 月份数）。这对生产环境（百万级 part）很重要。

`Stats` 输出四组信息：整体 `Total/Kept/Dropped`、按月的 `Months []MonthStat`、`NonPartitioned`（含 `NonPartitionedKept`，**空备份护栏依赖这个字段**，见 §3.4）、以及 `NonPartitionedSample`（最多 16 个路径样例，供人工核对）。

### 2.3 `report.go`：两种输出

- `RenderPlanTable()`：定宽对齐的文本表（`wMonth=18` 是为了容纳 `"(non-partitioned)"` 这个最长的首列值）。
- `EncodePlanJSON()`：机器可读计划，字段设计与 `Stats` 一一对应。

**这里有个刻意的取舍**：`HumanizeBytes` 没有引入第三方库（如 `humanize`），而是用 20 行本地实现（filter.go:258-269）。理由是本工具的依赖面已经因为 S3/GCS 后端而很大，不值得为格式化再加一个包。

## 3. `internal/backupaction` —— 备份编排

### 3.1 为什么必须自己写这段

见 `docs/01-调研与设计.md` §2.1。核心是官方把过滤点封死了：

```go
// lib/backup/actions/backup.go:28-48
type Backup struct {
	Concurrency int
	Src    *fslocal.FS        // 具体类型，不是接口
	Dst    common.RemoteFS
	Origin common.OriginFS
}

// lib/backup/actions/backup.go:111 —— 包内私有，外部不可调用
func runBackup(src *fslocal.FS, dst common.RemoteFS, origin common.OriginFS, concurrency int) error
```

### 3.2 `Options` / `Result`（action.go:52-114）

`Options` 是纯粹的输入参数（含 `MonthRange`、三个开关、两个护栏字段）；`Result` 是执行结果的量化汇总。

`Result` 里有一个字段值得单独说明：

```go
// OutOfRangePartsToDelete 是 -prune=true 时将被删除、但月份范围之外的目标端 part 数量，
// 是"误删历史备份"风险的量化指标。
OutOfRangePartsToDelete int
```

它把"这次会不会误删历史数据"从一个模糊的担心变成了一个**可断言的数字**。

### 3.3 `Plan` 与 `Run` 的分工（action.go:119-155）

```go
func Plan(snapshotPath string, opt Options) (*Result, error) {
	opt.DryRun = true                       // 强制置位，调用方无法误开
	p, err := buildPlan(snapshotPath, 0, opt)
	...
}
```

`Plan` 走的**与 `Run` 完全相同的 `buildPlan` 路径**，只是 `DryRun=true` 且在 `buildPlan` 末尾提前返回。这保证了"`-dryRun` 看到的计划"与"真正执行时的决策"**不可能不一致**——这是很多工具有意无意忽略的一致性要求。

`Run` 即使被传入 `opt.DryRun=true` 也会在 `buildPlan` 之后立即返回，不触发任何远端写操作。

### 3.4 `buildPlan`：过滤与两道护栏（action.go:271-369）

```go
// ① 列举
src := &fslocal.FS{Dir: snapshotPath, MaxBytesPerSecond: maxBytesPerSecond}
src.Init()
allParts, err := src.ListParts()
common.SortParts(allParts)

// ② 过滤（唯一的"侵入点"）
agg := monthfilter.NewAggregator(filter)
kept := make([]common.Part, 0, len(allParts))
for i := range allParts {
	if _, ok := agg.Add(allParts[i].Path, allParts[i].Size); ok {
		kept = append(kept, allParts[i])
	}
}
stats := agg.Stats()
```

**`kept` 这一个切片同时决定三件事**：上传什么、`-prune` 以什么为基准算差集、审计文件里记什么。三者永远一致。

**护栏 1 · 期望月份（action.go:332-339）**：`stats.MissingExpectedMonths(opt.ExpectMonths)` 非空则报错，错误信息里带上"快照实际存在的月份为 …"，让用户能立刻定位是记错了月份还是指错了存储。

**护栏 2 · 空备份（action.go:347-359）**——本次开发中发现并修复的真实缺陷：

```go
partitionedKept := stats.Kept.Parts - stats.NonPartitionedKept.Parts
if partitionedKept == 0 && !opt.AllowEmptyResult {
	return error("月份区间 %s 在快照 %q 中没有任何按月分区的数据 part（仅匹配到 %d 个非分区文件…）")
}
```

**朴素写法为什么错**：如果按"过滤后 part 总数为 0"判断，那么在默认 `-includeNonPartitioned=true` 下，`metadata/` 下的元数据文件总会通过过滤，于是"只含 metadata、还原后没有任何时间序列"的无效备份会被判定为"非空"而**静默放行**。把计数改为"按月分区的 part 数"，才真正拦住了这种情况。

### 3.5 `Run` 的执行顺序（action.go:133-246）

```go
① dst.DeleteFile(backupnames.BackupCompleteFilename)   // 先摘完成标记
② dstParts = dst.ListParts()
③ originParts = origin.ListParts()
④ notInBackup = common.PartsDifference(dstParts, kept)
   if opt.Prune {
       res.OutOfRangePartsToDelete = countOutOfRange(notInBackup, filter.Range)   // ← 新增的风险量化
       if res.OutOfRangePartsToDelete > 0 {
           logger.Warnf("目标端 %s 中有 %d 个 part 位于所选月份范围 %s 之外，本次将被删除…")
       }
       deleteParts(ctx, dst, notInBackup, opt.Concurrency)
   } else if len(notInBackup) > 0 {
       logger.Infof("-prune=false：目标端有 %d 个 part 不在本次备份范围内，将原样保留", len(notInBackup))
   }
⑤ partsToCopy = common.PartsDifference(kept, dstParts)
   originPartsToCopy = common.PartsIntersect(originParts, partsToCopy)
   copyParts(ctx, origin, dst, originPartsToCopy, opt.Concurrency)
⑥ uploadParts = common.PartsDifference(partsToCopy, originParts)
   uploadPartsFrom(ctx, p.src, dst, uploadParts, opt.Concurrency)
⑦ storeMetadata()  →  storeMonthRange()  →  dst.CreateFile(BackupCompleteFilename)
```

第 ① 步的"先摘完成标记"与第 ⑦ 步的"最后才写完成标记"是官方语义，必须保持：**只要完成标记存在，就代表这个备份目录是完整可用的**。中途失败会留下"无完成标记"的目录，从而不会被误当成可用备份。

第 ⑤ 步的 origin 服务端拷贝免下载；若 `CopyPart` 因跨后端类型失败，`copyParts`（action.go:474-493）会退化为 `downloadAndUpload`（action.go:497-522）——用 `io.Pipe` 边下边传，不落盘、不占额外磁盘。

### 3.6 `runParallelInternal`：并发原语（action.go:625-688）

官方 `lib/backup/actions/util.go` 的并发实现是包内私有的，因此这里重新实现了一份语义等价的版本。三个要点：

```go
resultCh := make(chan error, len(parts))   // ① 缓冲 = 任务总数
...
if err := f(p); err != nil {
	resultCh <- err                         // ② 永不阻塞
	cancel()                                // ③ 首个错误即取消
	return
}
```

- **① 缓冲容量 = 任务数**：保证 worker 发结果永不阻塞。如果缓冲是 1，读端一旦提前 `return`，剩余 worker 会永久卡在 `resultCh <- nil` 上，导致 `wg.Wait()` 死锁。
- **② 错误优先**：`wg.Wait()` 之后遍历 `resultCh`，取第一个非 nil 错误返回，避免"部分失败被淹没"。

`runWithProgress`（action.go:600-622）每 10 秒回调一次进度（与官方间隔一致），`uploadPartsFrom` 用它计算百分比与 ETA。

### 3.7 审计文件（action.go:384-443）

`storeMonthRange` 写出 `backup_month_range.ignore`。文件名的后缀选择有源码依据：`lib/backup/fscommon/fscommon.go:234` 的 `IgnorePath` 只判断 `.ignore` 后缀，而所有远端 `ListParts()` 都会调用它，因此该文件不会被当 part、不会被 prune 误删、不影响 vmrestore。

## 4. `cmd/vmbackup-partition/main.go` —— CLI 与生命周期

### 4.1 变量声明区（main.go:42-83）

前半段（main.go:43-62）**逐字复用官方 vmbackup 的参数声明**，包括帮助文案。这不是偷懒——参数语义完全相同意味着运维手册、监控告警、自动化脚本可以原样迁移。

后半段（main.go:64-83）是本工具新增的 8 个参数。

### 4.2 `main()`（main.go:85-186）

```
flag.CommandLine.SetOutput(os.Stdout)     ← 与官方一致，便于 grep/管道
envflag.Parse()                           ← 官方：支持 -flag=value 与 FLAG=value 两种形式
initSecretFlags()                         ← 脱敏 -snapshot.createURL/deletURL
buildinfo.Init(); logger.Init()

opt, err := buildOptions()                ← 解析本工具特有参数（护栏在此）
ctx, cancel := context.WithCancel(...)    ← 信号取消
go procutil.WaitForSigterm()

deleteSnapshot := func() {}               ← 先声明空函数
if len(*snapshotCreateURL) > 0 {
    ... flag.Set("snapshot.deleteURL", ...)  // 由 createURL 推导
    name, err := snapshot.Create(ctx, createURL)
    flag.Set("snapshotName", name)
    deleteSnapshot = func() { snapshot.Delete(context.Background(), ...) }
}

// -dryRun 分支：不启 HTTP 服务、不连远端
if *dryRun {
    res, err := backupaction.Plan(snapshotPath, opt)
    deleteSnapshot()
    ...
    printPlan(...)
    return
}

// 正式路径
go httpserver.Serve(...)                   ← /metrics
pushmetrics.Init()
runErr := runBackup(ctx, snapshotPath, opt)
deleteSnapshot()                           ← 无论成败都删
```

两个细节值得强调：

**① `deleteSnapshot` 先声明为空函数再赋值。** 官方注释（对应 issue #2055）解释了原因：`logger.Fatalf` 会直接 `os.Exit`，不会执行 `defer`。所以快照删除必须写成"在 `Fatalf` 之前显式调用"的形式，而不能依赖 `defer`。

**② 删除快照时不用 `ctx`。** 进程被 Ctrl-C 中断时 `ctx` 已被取消，若用 `ctx` 去调删除接口会立刻失败。代码里显式用了 `context.Background()`。

### 4.3 `buildOptions()`（main.go:206-244）

参数校验集中于此：必填检查、`ParseRange`（区间反转护栏）、`-expectMonths` 解析、`-concurrency > 0`。返回 `backupaction.Options`，让 `main` 与业务逻辑解耦。

### 4.4 `hasFilepathPrefix()`（main.go:369-393）

`-dst` 若为 `fs://` 且位于 `-storageDataPath` 内部，直接拒绝。逻辑与官方 `app/vmbackup/main.go` 的实现保持一致（先 `filepath.Abs`，再 `filepath.Rel`，用 `rel` 是否以 `.` 开头判断）。作用是把"备份写进数据目录、进而污染 vmstorage 数据"这个灾难性问题挡在启动阶段。

### 4.5 `usage()`（main.go:300-339）

用 `flagutil.Usage` 输出，帮助信息本身就是**可复制的操作示例**（4 个典型场景）。

## 5. `scripts/` —— 验证基础设施

### 5.1 `make-fake-snapshot.sh`

生成与真实 vmstorage 快照**逐项同构**的目录：

- `data/{small,big,indexdb}/<YYYY_MM>/<16位hex partID>/` 各含 `parts.json` 与数据文件；
- `data/<sub>` 是**相对符号链接**，目标为 `../../../data/<sub>/snapshots/<SNAP>`（三级上跳，对应 `fs.MustSymlinkRelative`）；
- `metadata/` 是实体目录；
- 文件内容确定性（基于 sha256 派生），保证可复现。

脚本末尾有**自检循环**：逐个 `data/<sub>` 验证符号链接可解析，避免"生成了一批谁也读不了的假快照"。

> 开发中曾把上跳写成二级（`../../data/...`），导致符号链接全部断裂、`ListParts` 返回空。这个自检就是为了把这类错误挡在验证之前。

### 5.2 `e2e-real.sh` / `e2e-synthetic.sh`

两个脚本的断言策略是**等价性对比**而不是硬编码期望值：

```bash
# 本工具在 [FROM, TO] 上的产物 == 官方 vmbackup 全量产物 ∩ [FROM, TO]
OFF_IN_RANGE="$(months_in "$DST_OFFICIAL/data/${sub}" | grep -E '^2026_0[2-6]$' ...)"
assert_eq "目标端 data/${sub} == 官方全量 ∩ [${FROM}..${TO}]" "$OFF_IN_RANGE" "$(months_in "$DST_TOOL/data/${sub}")"
```

**为什么这样写很重要**：真实 VM 在小数据量下不会产生 `big` part，如果硬编码"`data/big` 必须有 5 个月"，断言会因为环境差异而无意义地失败。用"与官方全量做交集"作为期望值，断言在任何数据量下都成立且有实际约束力。

### 5.3 `backup-cluster.sh`

Shell 编排：SSH 到每个 vmstorage，把 `-dst` 拼成 `${DST_PREFIX}/${nodeName}`，收集退出码并汇总。`--dry-run` 模式下改用 `-planOut=/tmp/backup-plan-<node>.json`，不做任何远端写入。

## 7. 开发过程中修正的三个真实缺陷

保留在此，作为后续维护的"已知踩坑清单"。

### 缺陷 1 · 空备份护栏判据错误（工具缺陷，已修复）

- **现象**：`-fromMonth=2026_10 -toMonth=2026_12`（快照中不存在）时，工具**没有**报错，而是"成功"写出一个只含 `metadata/` 的备份。
- **根因**：护栏按"过滤后 part 总数"判断，而 `-includeNonPartitioned=true` 下 `metadata/` 文件总会被保留。
- **修复**：改用 `stats.Kept.Parts - stats.NonPartitionedKept.Parts`（action.go:347），并同步更新 `-allowEmptyResult` 的帮助文案与 e2e 断言文案。
- **回归覆盖**：`e2e-real.sh` 步骤 9 中的 `区间无分区数据时默认拒绝写出空备份`、`拒绝原因说明只匹配到非分区文件` 两项。

### 缺陷 2 · 合成快照符号链接层级错误（测试设施缺陷，已修复）

- **现象**：合成快照生成成功，但 `ListParts` 返回 0 个 part。
- **根因**：`data/<sub>` 的符号链接写成二级上跳 `../../data/...`，而真实 VM 用三级 `../../../data/...`。两者差一层，链接全部断裂。
- **修复**：改为 `../../../data/<sub>/snapshots/<SNAP>`，并在生成脚本末尾加符号链接自检。
- **教训**：合成快照的"同构"必须逐项验证，不能凭印象。文件计数也因此需要用 `find -L`（跟随符号链接）。

### 缺陷 3 · 测试断言期望值写错（不是工具缺陷）

- **现象**：`e2e-synthetic.sh` 第 6 步断言 `-prune=false 追加后共存` 失败，期望含 `2026_01`，实际不含。
- **根因**：第一批只备份 `02..06`，第二批以 `-prune=false` 追加 `07..09`。`2026_01` 从未被备份，**实际结果 `02..09` 是正确的**；断言误用了"全部 9 个月"的常量。
- **修复**：断言改为 `"$EXPECT_KEPT 2026_07 2026_08 2026_09"`。
- **教训**：断言失败时先判断"是工具错了还是断言错了"。本例中工具行为完全正确。

### 附 · 脚本层的两个兼容性问题

- **macOS 自带 bash 3.2 不支持关联数组** `declare -A` → 改用函数 `official_in_range()` / `tool_months()`。
- **bash 3.2 在 `set -u` 下展开空数组会报 `unbound variable`** → 统一改用 `${arr[@]+"${arr[@]}"}` 惯用法（`scripts/build-linux-amd64.sh`、`e2e-real.sh` 的 `cleanup` 等）。
- **`$VAR` 后紧跟中文全角标点会被并入变量名** → 此类位置统一写 `${VAR}`。

这三个问题在 Linux（bash 5.x）上不会出现，但如果构建/调试机是 macOS，就会真实撞上。
