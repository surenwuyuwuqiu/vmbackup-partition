# 01 · 调研与设计

> 目标场景：3 节点 VictoriaMetrics 集群（vm-cluster），各 vmstorage 的数据目录包含 `2026_02` ~ `2026_09` 共 8 个自然月分区，需要**只备份 `2026_02` ~ `2026_06`**，目标执行环境 Linux amd64。

---

## 1. 需求拆解

| 编号 | 需求 | 约束 |
| --- | --- | --- |
| R1 | 只备份 `[2026_02, 2026_06]` 闭区间内的完整数据 | 区间外的月份必须不出现在备份中 |
| R2 | 备份产物必须可被**官方 vmrestore** 还原 | 不允许出现"自研格式"，不允许修改官方代码 |
| R3 | 3 个 vmstorage 节点都要执行 | 每个节点的备份写入各自独立的目标目录 |
| R4 | 运行在 Linux amd64 | 交叉编译产物需静态链接、无 libc 依赖 |
| R5 | 可审计、可验证 | 需要"先看计划再执行"的试运行能力与量化报告 |

**R2 是本设计最强的约束**，它直接决定了整体架构（见 §4.1）。

## 2. 调研结论

### 2.1 开源版 vmbackup 的能力边界

**结论：开源版 vmbackup 没有任何"按时间/月份选择"的能力，它只能整份备份一个数据目录。**

源码证据（v1.150.0）：

`lib/backup/actions/backup.go:28-48`

```go
type Backup struct {
	// Concurrency is the number of concurrent workers during the backup.
	Concurrency int

	// Src is backup source
	Src *fslocal.FS

	// Dst is backup destination.
	Dst common.RemoteFS

	// Origin is optional origin for speeding up full backup if Dst points
	// to empty dir.
	Origin common.OriginFS
}
```

- `Src` 是具体类型 `*fslocal.FS`（**不是接口**），`Run()` 只能表达"把 Src 目录完整备份到 Dst"，没有任何过滤钩子。
- 真正干活的是包内私有函数 `runBackup(src *fslocal.FS, dst common.RemoteFS, origin common.OriginFS, concurrency int)`（`lib/backup/actions/backup.go:111`）——**首字母小写，包外无法调用，也无法传参覆盖**。
- 备份流程是"列举 Src 的全部 part → 上传差集"，中间不存在任何可插入过滤逻辑的位置。

因此，**在不 fork 官方代码的前提下，无法通过配置让开源版 vmbackup 只备份部分月份。**

### 2.2 商业版 vmbackupmanager 的能力

**结论：用户判断正确。** 企业版 vmbackupmanager 通过"保留策略 + 备份管理器"提供按时间维度的选择与生命周期管理，官方文档明确其为企业版功能：

- <https://docs.victoriametrics.com/victoriametrics/vmbackupmanager/>

它解决的问题是"定期全量备份 + 按保留策略清理"，与本需求（**一次性、按自定义月份区间、选择性备份**）语义并不完全对齐；且需要企业版 License，不在本次可选范围内。

### 2.3 备选方案对比

| 方案 | 做法 | 是否满足 R2 | 评价 |
| --- | --- | --- | --- |
| **A. Fork 并改造官方 vmbackup** | 复制 `app/vmbackup` 与 `lib/backup`，在 `runBackup` 里插入过滤 | ✅ | 需要长期跟踪上游改动，每次升级都要重新 merge，维护成本高 |
| **B. 软链接拼装快照后再备份** | 先手工构造一个只含目标月份目录的快照，再跑官方 vmbackup | ✅ | 需要额外磁盘与拷贝时间；对 `indexdb` 与符号链接层级处理不当会破坏快照；无护栏，易误操作 |
| **C. 备份全量后删除远端多余月份** | 跑官方 vmbackup 全量，再按 part 路径删除区间外对象 | ✅ | 先把 8 个月全部上传再删掉 2 个月，网络与时间成本翻倍；删除动作本身是高风险操作 |
| **D. 复用官方 lib/backup，自研薄执行器（本方案）** | 直接 import 官方 `lib/backup/{common,fslocal,fsremote,actions}`，重新实现"列举 → 过滤 → 传输"这一段编排 | ✅ | **改动面最小、升级零成本**：只依赖官方稳定接口，上游升级只需重编译 |

**选定方案 D。** 理由：

1. 传输协议、并发调度、限速、S3/GCS/AzBlob 各后端、错误重试**全部复用官方实现**，不存在"自研协议兼容性"风险。
2. 过滤只发生在**源端列举之后**，产出的对象集合与"官方 vmbackup 备份一个只含目标月份的快照"在字节层面等价（这一点由端到端测试证明，见 `docs/03-使用与验证.md` §5）。
3. 官方 vmrestore **一行都不用改**。

## 3. VictoriaMetrics 存储布局事实（源码级）

设计必须建立在对布局的准确认知上。以下是 v1.150.0 源码核对结果。

### 3.1 分区目录名 = `YYYY_MM`

`lib/storage/time.go:72-76`

```go
// timestampToPartitionName returns partition name for the given timestamp.
func timestampToPartitionName(timestamp int64) string {
	t := timestampToTime(timestamp)
	return t.Format("2006_01")
}
```

调用点：`lib/storage/partition.go:195`、`lib/storage/table.go:502`。

即 **分区目录名严格等价于 Go 时间格式串 `2006_01`**，例如 `2026_02`。这给了我们一个**强判据**：目录名长度 7、第 5 个字符为 `_`、其余为数字、且月份在 1~12 之间。

### 3.2 存储目录常量

`lib/storage/filenames.go:23-32`

```go
const (
	smallDirname = "small"
	bigDirname   = "big"

	indexdbDirname   = "indexdb"
	dataDirname      = "data"
	metadataDirname  = "metadata"
	snapshotsDirname = "snapshots"
	cacheDirname     = "cache"
)
```

### 3.3 快照结构

快照创建逻辑见 `lib/storage/table.go:138`（`MustCreateSnapshot`）。快照目录结构为：

```
<storageDataPath>/snapshots/<snapshotName>/
├── data/                                    ← 符号链接（fs.MustSymlinkRelative，lib/fs/fs.go:205）
│   ├── small/<YYYY_MM>/<partID>/            ← 实体文件，经符号链接可达
│   ├── big/<YYYY_MM>/<partID>/
│   └── indexdb/<YYYY_MM>/<partID>/
└── metadata/                                ← 实体目录（租户与元数据）
```

**关键细节：`data/` 下的一级子目录是相对符号链接，目标是 `<storageDataPath>/data/<sub>/snapshots/<snapshotName>`（三级上跳 `../../../data/...`）。** 这一点在自研合成快照时必须精确复刻，否则 `fslocal.FS.ListParts` 无法遍历（本次开发中曾因写成二级上跳而踩坑）。

### 3.4 备份产物格式：**按 part 路径寻址，不依赖 parts.json**

这是整个方案能成立的**决定性事实**。

- 每个 part 文件在远端的对象名由 `common.Part.RemotePath()` 生成，格式为

  ```
  <prefix>/<path>/<FILESIZE>_<OFFSET>_<SIZE>
  ```

  还原时由 `common.Part.ParseFromRemotePath()` 解析回本地路径。
- `parts.json` 是 **partition 在本地维护** 的文件，会作为普通 part 被上传，但**远端的 parts 列表与还原决策都不依赖它**。
- 官方 vmrestore 的流程是：`ListParts()` → 计算差集 → 下载；它**不做**"完整性清单校验"。

**推论：只要远端对象集合完整覆盖了目标月份的所有 part 文件，vmrestore 就能正确还原。** 因此"在源端按 part 路径过滤"是安全的，不需要伪造任何清单文件，也不需要写 `parts.json`。

> 这一点已由 `scripts/e2e-real.sh` 第 7 步验证：用官方 vmrestore 还原本工具产出的备份，与快照逐字节比对不一致组合数为 **0**。

### 3.5 `small` 与 `big` 的区分

`getDstPartType` 依据分区数据量决定 part 落在 `small/` 还是 `big/`：只有当单个分区的数据超过 `getMaxSmallPartSize()`（数百 MB 量级）时才会产生 `big` part。

这意味着：**小数据量的测试环境只有 `small` part，测不到 `big` 路径**。因此本项目额外提供了"合成快照"验证通道（`scripts/make-fake-snapshot.sh`），用与真实 VM 完全同构的目录结构覆盖 `small` / `big` / `indexdb` 三条路径。

## 4. 设计

### 4.1 核心思路：源端过滤 + 零侵入复用

```
                    ┌──────────────────────────────────────────┐
                    │  官方 lib/backup（原样复用，不修改不 fork） │
                    └──────────────────────────────────────────┘
                                        ▲
                                        │ import
┌───────────────────────────────────────────────────────────────────────┐
│                      vmbackup-partition（本项目）                      │
│                                                                       │
│  ┌────────────────┐   ┌──────────────────┐   ┌──────────────────────┐ │
│  │ monthfilter    │   │ backupaction     │   │ cmd/main.go          │ │
│  │ 月份解析/分类   │◀──│ 备份编排 + 护栏   │◀──│ CLI + 快照生命周期    │ │
│  │ 统计/报告       │   │ 并发/限速/差集     │   │ dryRun / metrics     │ │
│  └────────────────┘   └──────────────────┘   └──────────────────────┘ │
└───────────────────────────────────────────────────────────────────────┘
        │                        │                          │
        ▼                        ▼                          ▼
   源端过滤决策            复用官方传输层            复用官方快照机制
   data/<sub>/<YYYY_MM>/…   fslocal / fsremote /     snapshot.Create /
                            s3remote / gcsremote /   snapshot.Delete
                            azremote
```

一句话概括：**把"列举源 part 列表"和"上传 part 列表"之间插一层月份过滤器，其余一切照旧。**

### 4.2 为什么必须自行实现那一小段编排

因为官方把这段逻辑**锁死在具体类型和私有函数里**（§2.1）。可在保持语义完全一致的前提下重新实现的部分仅有：

| 官方位置 | 本实现 | 是否保持一致 |
| --- | --- | --- |
| `actions.Backup.Run()` | `backupaction.Run()` | ✅ |
| `actions.runBackup()` | `backupaction.Run()` 主体 | ✅ |
| `actions.storeMetadata()` | `storeMetadata()` | ✅（字段名逐字相同） |
| `actions.deleteDstParts()` | `deleteParts()` | ✅ |
| `actions.copySrcParts()` | `copyParts()` | ✅ |
| `actions.util.runParallel()` | `runParallelInternal()` | ✅（含 context 取消与错误优先） |
| 无 | **月份过滤（新增）** | 🆕 |
| 无 | **空备份护栏、期望月份护栏（新增）** | 🆕 |
| 无 | **`backup_month_range.ignore` 审计文件（新增）** | 🆕 |

### 4.3 执行流程与决策点

```
① 解析参数（-fromMonth / -toMonth 必填，区间反转即刻拒绝）
        │
② 快照准备
   有 -snapshot.createURL → 调 /snapshot/create 创建快照，登记 defer 删除
   否则                    → 用 -snapshotName 指向既有快照
        │
③ -dryRun 分支 ── 是 ──▶ Plan()：纯本地计算，输出计划表 + 可选 JSON，结束
        │ 否
④ buildPlan()
   fslocal.ListParts() 列举全部 part
   └─▶ 逐 part 调 monthfilter.Classify() 分类
       ├─ 落在 data/<sub>/<YYYY_MM>/…  → 按月区间判定 keep/drop   【决策点 1】
       └─ 其它（metadata/ 等非分区路径）→ 由 -includeNonPartitioned 决定
   统计聚合 → Stats（各月 part 数、体积、keep/drop）
        │
   ┌────┴─────────────────────────────────┐
   │ 护栏 1：-expectMonths 指定的月份是否存在？  ── 缺失则报错退出
   │ 护栏 2：按月分区的 part 数是否为 0？        ── 为 0 且未 -allowEmptyResult 则报错退出
   └────┬─────────────────────────────────┘
        │ 通过
⑤ dst.DeleteFile(backup_complete.ignore)      ← 与官方顺序一致，先摘完成标记
⑥ dst.ListParts() / origin.ListParts()
⑦ notInBackup = PartsDifference(dstParts, kept)
   -prune=true  → 删除差集；若差集中存在"位于月份范围之外"的 part，打 WARN 告警【决策点 2】
   -prune=false → 原样保留，仅打 INFO
⑧ partsToCopy = PartsDifference(kept, dstParts)
   originPartsToCopy = PartsIntersect(originParts, partsToCopy) → 服务端拷贝（免下载）
⑨ uploadParts = PartsDifference(partsToCopy, originParts) → 并发上传（带限速与进度/ETA）
⑩ 写 backup_metadata.ignore → 写 backup_month_range.ignore → 写 backup_complete.ignore
```

### 4.4 关键设计决策

#### D1 · 过滤只发生在源端

过滤后得到的 `kept []common.Part` **同时**用于三个地方：上传列表、`-prune` 的差集基准、统计与审计。这保证了"上传的"与"认为该有的"永远一致，不会出现"删了该留的"或"留了不该有的"。

#### D2 · 非分区文件默认保留（`-includeNonPartitioned=true`）

`metadata/` 下是租户与索引元数据，体积很小（示例快照中 2 个文件 / 384 B），但与还原后的存储可用性相关。默认保留，即：

```
keep(part) =
    part 位于 data/<sub>/<YYYY_MM>/… 且 <YYYY_MM> ∈ [fromMonth, toMonth]
  ∨ part 不位于任何月份分区目录（非分区路径）且 -includeNonPartitioned=true
```

#### D3 · 空备份护栏必须按"按月分区的 part 数"判断

**这是开发过程中发现并修复的一个真实设计缺陷。**

朴素做法是"过滤后 part 总数为 0 就报错"。但在 `-includeNonPartitioned=true`（默认）时，`metadata/` 下的文件**总会被保留**，于是"只含 metadata 的无效备份"会被判为非空从而**放行**——而这样的备份还原后不包含任何时间序列。

正确做法：

```go
partitionedKept := stats.Kept.Parts - stats.NonPartitionedKept.Parts
if partitionedKept == 0 && !opt.AllowEmptyResult {
    return error("月份区间 %s 在快照 %q 中没有任何按月分区的数据 part …")
}
```

#### D4 · `-prune` 默认 true，但越界删除必须告警

官方 vmbackup 的语义是"把目标端对齐到本次备份"。本工具保持一致（默认 `-prune=true`），但额外做了一件事：**统计差集中有多少 part 位于所选月份范围之外**，若大于 0 就打印 `WARN`，明确提示"若想多批累积，请用 `-prune=false`"。

这个告警解决的是一个真实的高风险误用场景：用户先备份 `02..06`，再备份 `07..09` 到同一个 `-dst`，若忘了 `-prune=false`，第一次的 5 个月会被静默删除。

#### D5 · 审计文件用 `.ignore` 后缀

`backup_month_range.ignore` 记录本次备份的月份选择、快照中各月分布、keep/skip 计数与体积。

选择 `.ignore` 后缀的原因（源码核验）：`lib/backup/fscommon/fscommon.go:234`

```go
func IgnorePath(path string) bool {
	return strings.HasSuffix(path, ".ignore")
}
```

所有**远端** `ListParts()` 实现都会调用它（`fsremote/fsremote.go:56`、`s3remote/s3.go:326`、`gcsremote/gcs.go:132`、`azremote/azblob.go:179`），因此该文件：

- 不会被 `ListParts()` 列出 → 不会被当成 part；
- 不会被 `-prune` 的差集计算误伤；
- 不影响 vmrestore。

#### D6 · 复用官方的快照生命周期

`-snapshot.createURL` / `-snapshot.deleteURL` / `-snapshotName` 的行为与官方 vmbackup 完全一致，包括"失败时也要删快照"的处理（官方 issue #2055 的规避方式）。

## 5. 边界与已知限制

| 编号 | 限制 | 影响 | 缓解 |
| --- | --- | --- | --- |
| L1 | **集群备份不可合并** | 各 vmstorage 的 part 路径可能相同但内容不同，写入同一目录会互相覆盖 | 必须按节点写入独立目录；`scripts/backup-cluster.sh` 已强制 `<dstPrefix>/<nodeName>` |
| L2 | 集群 `-replicationFactor>1` 时节点间数据重叠 | 分节点还原后仍是"分片存储"，不能当成单实例历史库用 | 如需合并为单实例，需额外的数据合并工具（见 §6 延伸阅读）；本工具不解决该问题 |
| L3 | 不按 Tenant 过滤 | 区间内所有租户的数据都会被备份 | 本需求不需要；如需按租户过滤需扩展 `monthfilter` |
| L4 | 不处理 `cache/` 目录 | 快照中通常不含 `cache/` | 无需处理 |
| L5 | Go 工具链版本要求 | v1.150.0 的 `go.mod` 声明 `go 1.26.6` | 需 Go ≥ 1.26.6；详见 `docs/02-编译指南.md` |
| L6 | 交叉编译目标 | 本项目只在 darwin/arm64 上编译、在 linux/amd64 上运行验证 | 已在 darwin/arm64 上产出 linux/amd64 静态 ELF 并校验；如需 linux/arm64 有现成 `make build-linux-arm64` |
